# Cybertron 轻量化 Harness Loop 方案

版本：实现记录（2026-11-22）

范围：OpenCode V2 日常软件研发路径与 13 个常驻角色

## 1. 目标

Cybertron 将规划、编排、执行与验收分配给 13 个常驻角色，并以事件账本记录运行状态。常规任务在同一个 run 中完成「理解、计划、执行、验证、结算」；只有影响交付结果的歧义或需要专项授权的动作才停下来询问用户。

轻量化的目标是减少重复交接和固定流程门，同时保留确定性计划检查、OpenCode 实际权限检查、项目基线要求的人工授权，以及可核验的工具证据。

## 2. 角色职责

| Cybertron Agent | Cybertron 职责 |
|---|---|
| Prima（先觉天） | 默认入口及唯一运行编排者：接续 run、派发、跟踪、结算并回传证据。 |
| Alpha-Trion（钛师傅） | 工程文档、知识整理与扩展、飞书 Wiki 同步。 |
| Onyx-Prime（锐天骁） | 只负责代码库地图：仓库结构、模块关系、入口与调用路径。 |
| Vector-Prime（维克多） | 只负责 Git：历史、差异、基线、分支及获准的 Git 操作。 |
| Quintus-Prime（昆图斯） | Debug 专家：复现和分析故障、验证假设、定位根因并给出修复建议；同时提供接口、HAL 和工程脚手架设计支持，不直接修改业务代码。 |
| Solus-Prime（赛天骄） | 唯一常规代码修改角色：功能实现、缺陷修复、重构、解耦、优化和移植。依据 Quintus 的诊断实施修改。 |
| Amalgamous（幻化天） | 临时专才入口：按需定义临时角色的任务、工具和约束；不得扩展注册权限或改写角色配置。 |
| Micronus-Prime（微米天） | L1 质量检查：规范、类型、静态分析和常见风险。 |
| Liege-Maximo（谎言天尊） | L2 深度审查：逻辑、架构、接口、并发和安全边界。 |
| Alchemist（炼金术士） | 完整承担测试：测试策略、测试编写、测试运行、场景执行和真实测试回执。 |
| Nexus-Prime（合体天） | 完整承担部署流程：构建准备、打包、部署执行和结果处理。 |
| Megatronus（震天尊） | 验证负责人：按验收条件核验成果和证据，给出验证结论。 |
| Thirteenth（第十三天尊） | 只负责意图分析和架构计划：理解目标、判断关键歧义、设计方案、拆分计划、定义验收条件并修订计划。保留 `mode: all`。 |

Alchemist 运行测试并记录退出码。Megatronus 对照验收条件独立核对回执。

## 3. 角色入口与交接

支持两种进入同一 Harness Loop 的方式：

1. **Prima 入口**：Prima 接收新需求，派 Thirteenth 理解意图并创建计划；计划提交后 Prima 直接派发就绪节点。
2. **Thirteenth 入口**：用户通过 Shift+Tab 直接与 Thirteenth 制定计划；Thirteenth 创建的 run 可以由 Prima 接续，无需用户手动复制 run ID。

两种入口都保留同一个 run、同一个版本化计划和同一套事件账本。Prima 不编写计划；Thirteenth 不派发和结算执行节点。

## 4. Harness Loop

```text
用户意图
   ↓
Thirteenth 理解目标、制定验收条件和计划
   ↓ 计划提交时内核校验依赖、角色、写入范围、验证可执行性
Prima 派发 ready 节点
   ↓
执行角色返回产物与工具反馈
   ↓
Prima 收集状态和真实回执
   ├─ 计划仍成立 → 回读或核验真实回执 → Prima 结算
   └─ 反馈推翻假设 → Thirteenth 在同一 run 修订受影响节点 → Prima 继续派发
```

### 4.1 常规任务

- 明确的项目内需求直接形成最小可行计划并派发。
- 仅当歧义会改变交付内容、写入目标、风险或验收标准时，Thirteenth 才使用原生问题工具澄清。
- 单文件、精确内容任务优先一个节点；若目标内容已满足，内核可通过回读和哈希证据结算，无需重复写入。
- 删除、飞书写入、设备操作、烧录和远程部署继续执行项目基线中的专项授权要求；普通明确需求不因此触发额外确认。

### 4.2 计划提交与确定性校验

计划提交和修订时由内核执行确定性检查，包括：

- 图结构、依赖关系、循环和节点状态。
- capability 与执行角色绑定、角色写入范围和硬拒绝路径。
- 每个验收条件是否有节点覆盖。
- 必需验证是否有可用工具、正确角色、覆盖节点和可结算的回执类型。
- 新计划内容摘要、版本号和账本事件。

校验失败时返回具体节点、原因和允许修订的字段，Thirteenth 可据此修订。常规路径不要求 Prima 再单独启动计划评审模型步骤。OpenCode 仍是实际工具权限的最终执行方。

### 4.3 同一 run 重规划

- Prima 将当前 run ID、计划版本、失败诊断、执行事件和已有回执交给 Thirteenth。
- Thirteenth 基于当前版本修订剩余计划；内核拒绝过期版本、在途节点冲突及越权写入范围。
- 已完成且输入未失效的节点和有效回执继续保留。
- 只重新调度被变更节点、其受影响依赖和确实失效的验证节点。
- 可恢复的局部故障使用有限重试；初始假设被证据推翻、重复失败或验证策略改变时触发重规划。
- 用户改变交付目标时才创建新 run，并记录与旧 run 的关系。

### 4.4 按任务选择验证

- Thirteenth 根据需求、计划、实际 diff、风险和可用验证工具选择验证方式。
- Alchemist 负责实际测试和测试回执；Micronus、Liege-Maximo 分别承担需要的 L1/L2 审查；Nexus 承担构建和部署；Megatronus 核对最终验收证据。
- 内核在计划提交时拒绝无法执行或无法结算的必需验证，并说明缺少的工具、绑定或证据类型。
- 完成状态只能由受信任内核验证器和真实工具回执产生。模型自然语言、子代理自述或模拟宿主回调不能冒充真实工具报告。
- 验证门按任务风险和用户验收要求决定，不要求每个任务固定经过完整 L1、L2、测试、构建和部署流水线。

## 5. 安全与权限边界

- `cybertron/registry.py` 仍是角色权限源头；导出的 OpenCode 配置和 agent prompt 由生成流程产出。Amalgamous 创建临时专才不能编辑权限源或扩大已注册权限。
- OpenCode 执行真实权限判定；本地 `policy.py` 只用于自检。
- Prima 负责执行派发与结算，不因此获得业务源码写权限。
- 所有写节点声明窄 `write_scope`；项目配置、Git 元数据和运行账本继续受保护。
- Nexus 的部署权限不绕过具体动作授权。物理烧录、设备上电和远程部署仍要求明确目标、固件、操作范围、回滚方案和人工审批。
- 测试与 L1/L2/部署结果必须保存结构化证据；对外报告应区分真实工具回执、内核校验结论和模型摘要。

## 6. 常规路径与证据

| 常规流程中的成本 | Cybertron 的处理方式 |
|---|---|
| 计划展示后固定等待确认 | 明确需求直接规划；关键歧义才提问；提交时内核确定性校验。 |
| 每个 unit 通过文本信号逐阶段推进与提交 | 以同一个 run 的计划节点、状态事件和真实工具回执推进。 |
| 多个固定质量门按流水线顺序触发 | Thirteenth 按任务、diff 和能力选择验证；必要门在提交时校验可结算性。 |
| 失败后回到独立流程或新计划 | Prima 将反馈送回 Thirteenth，同一 run 版本化修订并复用有效证据。 |
| 编排者依赖 specialist 摘要维护流程状态 | 以持久化事件账本和内核状态作为运行事实，模型摘要只负责解释。 |

## 7. 验收场景

| 场景 | 验收标准 |
|---|---|
| 明确项目内单文件任务 | 无人工确认、无独立计划评审步骤，在首个 run 完成；由精确内容回读或真实写入回执证明结果。 |
| Python 回归测试推翻初始判断 | 临时项目中真实测试失败；Prima 将失败回执交给 Thirteenth；同一 run 计划版本增加；未受影响节点和有效回执复用；真实测试再次通过后结算。 |
| Shift+Tab 单独规划，Prima 接续 | Thirteenth 直接创建计划；Prima 能发现并接续同一 run，正常派发、跟踪和结算。 |
| 必需验证不可执行 | 计划提交被内核拒绝并返回缺失能力和可行动原因，不能凭模型口头声称完成。 |
| 版本冲突和节点复用 | 过期 revision 被拒绝；有效完成节点不重复调度；变更导致输入失效时仅重跑受影响验证。 |
| 权限专项回归 | 显式只读不写入；外部文件遵循精确授权；飞书、设备、烧录与远程部署保留对应人工审批和操作约束。 |

## 8. 实施顺序

1. **压缩常规路径**：明确意图直达规划与派发；提交和修订时进行内核校验；撤掉 Prima 单独启动的常规计划评审步骤。
2. **打通同一 run 重规划**：建立 Prima 到 Thirteenth 的显式规划交接，附带版本、诊断和证据；在同一 run 修订并保留有效节点结果。
3. **完成验证闭环**：将 diff 和可用验证能力交给 Thirteenth；让内核拒绝无法结算的必需验证；以真实工具回执结算测试和验证结果。
4. **同步角色导出**：根据角色源重新生成根目录与测试目录配置，核对 Markdown 与 JSON 权限一致，再运行 OpenCode 配置诊断。
5. **运行验收并留存证据**：执行 AGENTS.md 指定的 Python 验收、涉及的 Node 插件测试和三个端到端场景，保存结构化回执。
