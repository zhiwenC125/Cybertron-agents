# Cybertron 模型配置与混合编队：产品终版方案

日期：2026-11-15

状态：**用户已审核；已在公开 `0.2.0` 实现并发布。**

依据：[当前开发计划](../../DEVELOPMENT_PLAN.md)、[阶段 E 验收](../stages/E-opencode-orchestration.md)、[项目安全基线](../../AGENTS.md)。

## 1. 用户要得到的结果

安装 Cybertron 后，用户只配置一次模型编队，之后仍在 OpenCode 中用 Shift+Tab 选择 `prima` 并输入自然语言，或在 Build 中使用 `/cybertron <需求>`。十三个角色按各自的模型映射执行；OpenCode 原有 Build/Plan 默认行为不变。

同一套功能须覆盖：

1. 公司的一把 API Key 对应约 38 个模型，用户把模型分为高、中、低三档，再分配给十三个角色。
2. 私人使用多个厂商、每个厂商各有一把 Key；十三个角色可以跨厂商混编。
3. Key 已经配置在电脑上的 OpenCode 认证或服务环境中时直接复用，不要求重新输入。
4. Key 只在其他工具或任意本地文件中时，指引用户通过 OpenCode 的认证入口接入，不扫描、读取或迁移原始密钥。

角色、权限、系统提示词仍以 `cybertron/registry.py` 和导出器为准。模型选择是安装后的本机配置，不改变角色权限。软件任务不会因为给 `megatronus` 分配模型而获得物理操作授权。

## 2. 产品入口与日常路径

| 入口 | 作用 | 是否输入密钥 |
| --- | --- | --- |
| `cybertron models setup` | 首次配置或随时重配：显示现有编队，可只改一个角色、调整三档或全部重配 | 否 |
| `cybertron models show` | 查看当前项目最终生效的十三角色映射、作用域及配置来源 | 否 |
| `cybertron models doctor` | 检查 OpenCode 连接、模型可用性、角色加载和配置漂移 | 否 |
| `cybertron models rollback` | 查看本机历史编队并恢复上一份可用配置 | 否 |
| OpenCode `/connect` 或 OpenCode 服务环境 | 由 OpenCode 建立供应商认证 | 是，仅在 OpenCode 的认证流程中 |

三种安装方式（npm、Python/pipx、GitHub Shell）安装后必须按渠道打印可执行入口：npm 打印 `npx -y cybertron-agents@<version> models setup`，pipx 打印 `cybertron models setup`，Shell 打印 `${目标}/bin/cybertron models setup` 的绝对路径；不得统一假设 `cybertron` 已在 PATH，也不得悄悄修改用户的 PATH。未配置时，`doctor` 说明角色仍采用发行包默认模型，不把“已安装”误报为“公司模型已配置”。

日常 OpenCode 对话中不要求用户再次选择模型。`/cybertron` 是开发工作流快捷入口，不承担收集 Key 的职责。若编队未就绪，工作流在调用任何角色模型之前提示具体缺项及 `models setup` 入口。

## 3. 向导完整流程

### 第一步：选择作用域与检查现状

默认推荐“当前用户所有项目”；也可选“仅当前项目”。向导展示当前生效配置及来源、是否存在项目级覆盖、已安装的 Cybertron 版本。再次运行同一命令时先展示现有十三行映射，提供“只改指定角色”“调整三档默认模型”“全部重配”“退出不保存”四种操作；未选中的角色保持原模型。项目级配置覆盖全局编队时必须提供全部十三角色映射，避免公司项目无意继承私人供应商。

通过 OpenCode 提供的非密钥接口查询账号连接状态与可用模型，不读取认证数据库、不显示 Key、不把凭证值写入任何日志。若已有 Key 且 OpenCode 可使用，直接进入模型选择。若 Key 只存在于终端环境，检查运行模型请求的 OpenCode 服务是否也能看到该环境；仅 shell 看得到而服务看不到时给出可执行的修复指引。

### 第二步：发现或接入模型

按供应商分组展示 OpenCode **当前项目实际可用**的模型，支持搜索、过滤和查看模型 ID；一个公司网关可以显示 38 个模型，多个私人供应商也可同时显示。模型未出现在 OpenCode 可用列表中时不得假装可选。

对于自定义公司网关，向导可协助填写非密钥元数据：供应商名称、接口地址、兼容协议、模型 ID 清单与环境变量**名称**。保存前展示将写入 OpenCode 配置的差异，保留原有 JSONC 内容和回滚副本。Key 仍通过 OpenCode `/connect` 或其服务环境接入。自动发现不到清单时允许导入/逐项填写模型 ID；不得凭一个 Key 推断模型权限、实际数量或能力。

### 第三步：建立高、中、低三档

用户从已可用的模型中为三档各选一个**主模型**，可为某档登记多个候选模型供手动改选。若公司已有分级清单，可以按清单导入；没有清单则由用户指定，向导不凭名字或价格自动判断档次。38 个模型是可选目录，不意味着一次任务会同时调用 38 个模型。

编队模板：

- **单模型**：十三角色都使用同一模型，适合个人快速试用。
- **三档推荐**：高阶给 `prima`、`solus-prime`、`liege-maximo`、`megatronus`；低阶给 `onyx-prime`、`vector-prime`；其他七个角色使用中阶。只是可修改的初始方案，不表示某个具体模型已通过能力验证。
- **逐角色自定义**：任意角色可从所有已可用模型中改选；支持跨供应商编队。展示完整十三行表、角色职责、选中模型与供应商。

第一版按**明确的每角色主模型**派单，不按自然语言动态猜测模型，不自动在 38 个模型间轮换。模型失败时默认阻塞，用户在向导中手动改选。自动备用与动态成本路由留待后续独立设计，并须以显式允许的供应商范围为前提。

### 第四步：检查与启用

保存前先做本地检查：十三角色均有模型、模型 ID 属于 OpenCode 当前可用目录、公司作用域未引用禁止的个人供应商、角色权限与发行包基线一致。可选的在线检查逐个测试**实际被选中的不同模型**，使用不含项目文件的短提示；验证连接、工具调用与结构化回复能力，提示可能产生少量费用。未运行在线检查时明确标为“未实测”，不得显示“全部可用”。

向导展示变更前后完整十三行映射，突出本次实际改变的角色与受三档调整影响的角色，并列出改动文件。用户确认后原子写入配置；取消则不写入。保存后运行 OpenCode 的实际配置/角色诊断，并核对每个角色的最终模型。失败时恢复上一份可用编队，输出可执行的修复步骤。历史配置可用 `cybertron models rollback` 显式恢复。配置完成页给出 `opencode`、Shift+Tab 选 `prima` 的使用步骤，并说明重新打开或刷新现有 OpenCode 会话后新编队才用于新任务。

## 4. 配置、调用与升级规则

- 全局模型编队存于用户本机 Cybertron 配置目录；项目编队存于被 Git 忽略的项目级 `.cybertron/`。只保存模型 ID、档次、供应商允许范围及配置版本，不保存 Key、令牌或认证数据库内容。需要团队共享时，另导出不含凭证的模板，由公司人员自行审查后提交到公司仓库。
- 配置层次清晰：项目级完整编队优先于全局完整编队；无编队时使用发行包默认模型并醒目提示。公司严格模式要求全部十三角色均在公司允许的供应商/模型范围内，任何缺项都阻塞，不能悄悄回落到个人 DeepSeek。
- 导出器和三种安装器只从权限事实源生成角色权限，再叠加本机模型映射。更新安装包后自动重应用映射；用户手工改过的安装目标先做差异检查和备份，拒绝覆盖无法安全合并的内容。根目录开发用生成物继续由一致性测试约束。
- 运行开始前记录所选编队的不可变摘要；每次派单记录角色、实际 `provider/model`、宿主会话引用及结果。重新运行 `setup` 后，**新 run 使用新编队**；既有 run 仍关联原编队。配置在运行中发生变化时停止继续派单，要求用户明确以原配置完成或开启新 run；不能静默混用两套编队。公开验收摘要不复制公司模型目录、接口地址、密钥或项目文件。
- OpenCode 会单独保存会话选中的模型，Shift+Tab 切换主角色不保证改动会话模型。开发必须验证 `prima` 在自然语言入口和 `/cybertron` 入口的**实际模型**均与编队一致；如宿主无法保证，须明确提示并阻止标记为配置成功。子角色派单也以实际宿主回执校验，不能只检查 Markdown 文本。
- 模型不可用、认证失效、网关限流、工具不兼容时指出角色、供应商、模型和失败阶段；不打印请求中的项目文件或密钥，不自动跨供应商重试。已有 `outcome_unknown` 派单继续沿用不可自动重试的规则。

## 5. 验收场景与发布门槛

1. 假公司网关：一份认证对应 38 个模型；选择三档主模型及个别角色覆写，十三个角色实际映射与预览完全一致。
2. 私人混编：多个供应商、各自独立认证；角色真实派单分布到指定供应商，当前会话选别的模型也不会造成无提示偏离。
3. 二次配置：再次运行 `setup` 只替换一个角色后，其余十二个模型不变；调整某档时预览所有受影响角色；取消无写入；回滚恢复上一份配置；旧 run 不因切换而静默改模。
4. 已有认证：OpenCode 账号和服务环境两种路径均可复用；只在其他工具中保存的 Key 会获得接入指引；CLI 输出、测试回执、Git 差异和软件包均无凭证。
5. 错误路径：缺少账号、选中模型未登记或下线、能力检查失败、限流、无权限、配置文件损坏、项目覆盖全局、升级冲突，均给出明确状态且不留下半配置。只需登记实际选用的模型；38 个模型尚未全部登记时给出目录不完整提示，不阻止已登记模型的使用。
6. 三种安装路径在干净临时项目做 dry-run、apply、重复安装、升级、回滚与 `doctor`；核对权限导出一致、Markdown/JSON 实际模型一致、`opencode2 debug config` 和 `debug agents` 加载结果一致。
7. 在获授权的临时项目完成一次真实软件九步流程，记录各角色实际模型、L1/L2 宿主证据、隔离测试回执、重放校验。无需调用公司真实 Key 完成本地自动化测试；公司环境的在线连通性由用户在公司机器上执行。
8. 运行项目既有验收：`python3 -m unittest discover -s tests -v`、`python3 -m cybertron.stage5_verify`、`python3 cybertron_primes_engine.py`。每个实施小阶段沉淀文档并提交；`0.2.0` 已经完成 npm、PyPI 与固定 GitHub 归档发布，验收见[发布记录](../stages/I-release-020.md)。
